### 첫 개선 묶음

1. **실행 입력과 과거 증거 계보 분리**: 실제 실행 코드·의존성·후보·설정·대상 빌드는 매번 fresh 확인한다. 과거 원본·실패·소스 snapshot은 보존하고 봉인된 묶음 manifest로 관리한다. 전체 감사는 작업 묶음의 시작·종료 및 최종 Gate에 배치한다. 오래된 증거를 현재 PASS로 재발급하지 않는다.
2. **성공 관측 재사용 조건 명시**: 코드, 전이 의존성, fixture, 설정, target build의 fingerprint가 같은 경우에만 재사용한다. 변경된 공통 모듈의 영향 검사는 다시 수행한다. mtime만으로 동일성을 인정하지 않는다.
3. **실행기 하나와 불변 RunSpec**: 세대마다 전체 실행기를 복제하지 않고 버전 있는 실행기와 작은 어댑터를 사용한다. 과거 실행기·영수증은 보존한다. 실행 권한, 한 번 실행 claim, 실패 후 재시도 금지는 RunSpec에 남긴다.
4. **실제 API 계약을 초기에 확인**: 승인된 실행 안에서 옵션·반환형·선택 범위의 작은 확인을 먼저 수행한다. mock이 실제 API 동작을 보장한 것처럼 사용하지 않는다. 전체 문서 본문을 매번 수집하는 방식도 필요한 조건으로 좁힌다.
5. **사례별 결과를 먼저 안전하게 저장**: 종료·정리 중 문제가 생겨도 완료한 사례의 원본과 판정 근거를 복구할 수 있게 한다. 부분 성공은 보존하되 실패한 묶음 전체의 성공으로 승격하지 않는다.

설계 검증에서는 실행 의존성 누락, 중간 변조, 오래된 입력, 잘못된 재사용, cleanup 실패를 의도적으로 넣어 거부되는지 확인한다. CPU·RAM/commit95%, 소유권·정확한 PID·입력·출력 검증은 유지한다. 코드 준비 검사의 첫 성능 목표는 현재 약322초에서 30초 이내로 줄이는 것이며, 아직 측정된 개선 결과는 아니다.

## 병렬 작업 배치

4개 작업 슬롯을 기준으로 한다. 첫 묶음에서 공통 병목을 제거한 뒤 같은 슬롯을 기능 마감으로 바꾼다. 이번 조사의 병렬 분석3개는 읽기 전용으로 수행했으며 구현 작업을 시작한 것은 아니다.

| 슬롯 | 첫 묶음 | 다음 묶음 | 소유 경계 |
|---|---|---|---|
| 0 조정·통합 | 수용 기준·영향 의존성·실행 큐·통합 관리 | 동일 | canonical 상태, 공통 schema, branch 통합·커밋 |
| 1 검증기 | 현재 입력/과거 계보 분리, RunSpec, 지속 결과, 변조·캐시 음성 검증 | F01/F03~F08/F16 필드·양식·각주·메모 | 검증 공통 모듈을 먼저 고정한 뒤 제품 모듈로 이동 |
| 2 제품 경로 | C05 실제 요청부터 검증된 출력·head까지 대표 경로 하나 | S01~S08 검색·치환·정규화·정렬·서식 | 공통 route/daemon 계약은 한 담당이 관리 |
| 3 참조·흐름 | F11 현재 부족한 Native API 계약과 C01~C04 필요한 범위 | F02/F09~F15 번호·책갈피·참조·차례·색인·인용·메일머지 | 제품 semantics/source target 모듈, 필요한 fixture/어댑터 |

각 작업은 별도 브랜치/checkout과 자기 출력 디렉터리를 사용한다. 공통 파일은 담당 한 명이 수정하고 나머지는 계약을 받아 구현한다. 원본 fixture·실패 증거·기존 실행 snapshot은 공유 읽기 전용이다. 각 스레드가 전체 저장소를 순환 검사하거나 같은 문서를 동시에 수정하지 않는다.

빌드, 전체 해시 감사, 실제 한글 작업은 공용 실행 대기열에서 한 번에 하나만 실행한다. 스레드마다 큰 target 디렉터리와 전체 Cargo 빌드를 복제하지 않는다. 구현 중에는 변경 모듈에 필요한 작은 검사만 요청하고, 통합된 상태에서 공통 빌드를 한 번 수행한다. source/target/workspace가 달라지면 해당 검사 재사용을 무효화한다.

실제 한글은 독립 재열기 조건을 보존한다. 세션을 무조건 합치거나 동시에 여러 한글을 띄우지 않는다. 사용자 명령 왕복은 외부 검증 host 한 번 준비 후 명시된 실행 요청을 받는 방식으로 줄일 수 있다. 작업 범위·claim·자원·소유권 검증과 접근 허용은 유지하며, 불확실한 실행을 자동 재시도하지 않는다.

## 가장 빠른 실행 순서

1. 이번 조사·진행안과 현재 구현을 보존해 원격에 푸시한다. 목표는 일시정지를 유지한다.
2. 재개 시 현재 코드 검사의 322초 기준을 사용해 검증 범위 분리부터 설계·검증한다. 소스 변조/의존성 누락을 잡으면서 읽기 횟수·바이트·시간이 줄어드는지 측정한다.
3. 이와 병렬로 C05 대표 요청 하나를 실제 결과 저장·revision/head까지 닫는다. 내부 library PASS와 실제 설치·사용 경로를 분리해 기록한다.
4. F/S별 현재 지원 코드를 공통 경로에 연결한다. 표의 담당이 같은 파일을 동시에 수정하지 않도록 순서를 조정한다. F11 하나의 수용을 기다리며 다른23개 F/S 묶음을 세우지 않는다.
5. C06 실제 시험은 바뀐 코드의 영향과 필수 실제 의미에 따라 중복 제거한 큐로 모은다. 기존158 수용 관측과 직접 영향 없는 성공을 재실행하지 않는다. 새로 도착한773은 재실행 없이 기존 산출물의 독립 제품 판독으로 이어간다.
6. P09의65기능별 계약·실제 경로·필요 실물·거부·증거를 C07에서 합쳐 Gate를 판정한다. 큐 완료나 모델 PASS만으로 Gate를 닫지 않는다.
7. P09가 닫히면 P10의 미마감 자동화부터 진행하고 P11/P12 기능, P13 검증 서비스, P14~P17 통합의 의존성을 따라 병렬 배치한다. 기존 scoped PASS는 재구현하지 않는다.
8. P18 통합 RC → P19 실제 배포·외부 절차·GA → P20 최초 산출물과 운영 주기로 이어간다.

현재 목표의 “P09 Gate 전 새 P10 구현 금지”는 유지한다. 후속 단계의 새 구현까지 미리 병렬 진행하려면 이 순서 규칙을 명시적으로 바꿔야 한다. 병렬 작업 허용을 그 규칙 변경으로 확대 해석하지 않는다.

## 완료량과 예상기간을 계산하는 방식

기능 수, WBS 카드 수, 영수증 수, 준비 검사 수로 완료율을 계산하지 않는다. 각 기능은 기존 core/import, 실제 request/backend, 검증된 output/head, 필수 Native/reopen, 음성 조건, 최종 registry/Gate를 구분해 추적한다. 각 기준에 최신 근거·의존성·담당·정확한 상태를 붙인다.

첫 개선 묶음 후 코드 검사 시간, 통합 빌드 수, Native 사례당 시간, 실제 제품 경로를 닫은 수를 측정한다. 그 관측 처리량으로 다음 묶음의 범위를 예측한다. 현 상태만으로 몇 주/몇 달 또는 병렬화 몇 배를 약속할 근거는 없다. 한 번의 작은 수정마다 수분의 전체 준비비와 사용자 왕복이 붙는 현재 방식을 먼저 바꾸는 것이 우선이다.
