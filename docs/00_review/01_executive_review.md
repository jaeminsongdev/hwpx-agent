# 상세 설계 검토

> 기준일: 2026-08-31  
> 프로젝트 코드명: `hwpx-agent`  
> 문서 세트 버전: `2.0-design`  
> 규범 키워드: **MUST/SHALL=필수**, **SHOULD=권장**, **MAY=선택**


## v1의 강점

v1은 초기 설계에서 흔히 빠지는 네 가지를 이미 해결했다. 첫째, 파일 형식 XML을 LLM에 직접 노출하지 않고 IR을 두었다. 둘째, 수식을 이미지가 아니라 native equation으로 정의했다. 셋째, mutation과 프로젝트 revision을 분리했다. 넷째, Web과 Codex의 상태를 원격 서비스에 두었다. 이 네 결정은 v2에서도 유지한다.

## v1의 구조적 한계

### 1. 제품 범위와 IR의 불일치

제품 목표는 한/글 문서 전반이지만 IR은 문단·제목·표·그림·수식·나누기만 표현했다. 따라서 다음 기능은 모델링할 곳이 없었다: 구역별 바탕쪽, 문서 그리드, 번호 시작값, 다단 세부 설정, 문단 띠, 글맵시, 차트, OLE, 양식 개체, 필드, 책갈피, 상호 참조, 각주·미주, 차례·색인·참고문헌, 변경 추적, 메모, 보호, 문서 이력, 접근성 메타데이터.

### 2. HWPX와 한/글 기능을 동일시

HWPX는 많은 문서 의미를 보존하지만, 한/글의 모든 UI·외부 서비스·변환·자동화 기능이 공개 스키마만으로 동일하게 재현되는 것은 아니다. 완전한 기능 목표에는 실제 한/글 자동화 경로와 버전별 검증이 필요하다.

### 3. 백엔드 선택 규칙 부재

“Python 우선, Rust로 이전”만으로는 어떤 기능을 어느 엔진에서 처리할지 결정할 수 없다. v2는 capability 단위로 선호·대체 백엔드, 사전 조건, 실패 정책, 검증 수준을 등록한다.

### 4. 제품 운영 현실 누락

Windows interactive desktop 요구, modal dialog, process hang, 파일 보안 승인 모듈, 상업 라이선스, 워커 이미지 버전 관리, 폰트 설치, 프린터 드라이버, 세션 고립이 설계에 없었다.

### 5. 플러그인 UI 표준 갱신 필요

최신 OpenAI 플러그인 설계는 MCP tools를 먼저 완성하고, UI는 MCP Apps bridge를 기준으로 부착하며, `window.openai`는 추가 확장으로 사용하는 방향이다. v2는 이 패턴으로 widget을 재설계한다.

## 수정 원칙

- “기능을 구현한다”는 말을 `operation schema + capability binding + backend + test + evidence` 묶음으로 정의한다.
- UI 메뉴 단위 기능과 문서에 저장되는 의미를 분리한다.
- 비결정적인 자동화는 deterministic operation plan과 evidence receipt로 감싼다.
- 한 번의 사용자 요청이 여러 백엔드 단계를 거칠 수 있도록 job DAG를 사용한다.
- 완전성을 기능 수가 아니라 **전 기능 disposition 100%**로 측정한다.
