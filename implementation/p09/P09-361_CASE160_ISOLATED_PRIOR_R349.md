# P09 이전159 검사의 설정 분리

기본 설정을 다음 실행 대상인 160번에 유지하면서, 이미 승인된 159번의 원래 전체 검사를 독립 설정으로 수행하는 연결을 검증했다. 공식 승인 수는 153/249이며 잔여 개별 사례는 96개다. 이번 결과는 160번 제품 실행이나 P09 완료 판정이 아니다.

## 설정 분리와 검사 보존

원래 159번 함수군은 코드, 기본값, closure 및 keyword 기본값을 유지한 채 별도 환경에 연결했다. 전체 입력 admission과 그 하위 의존성, frozen prepare는 실제 159번 설정을 사용한다. 기본 160번 설정을 임시 교체하지 않으며, 원래 graph와 checkpoint도 변경하지 않는다.

독립 검사는 이미 저장된 실제 159번 결과에 원래 제품·Native·자원·정리·엄격한 실행 창 oracle을 적용한다. 관측 결과를 고치거나 이전 제품 실행을 반복하지 않는다. 두 실제 byte boundary도 그대로 확인한다.

## 실패 보존과 수정 결과

첫 시도 r762에서는 코드 테스트 9개가 통과했으나, 하위 의존성의 설정이 기본 160번에 남아 `CURRENT_EPOCH_ACCEPT_EXACT159_CURRENT_BINDING_CONFIG`로 전체 검사가 실패했다. 실패 기록은 보존했다. 하위 `old.base`도 private159 설정에 연결한 다음 r763을 수행했다.

r763은 코드 테스트 9개와 원래 전체 검사를 통과했다. 입력 221개의 fresh 및 최종 hash 확인이 일치했으며 cleanup은 true다. 해당 실행에서 시스템 CPU 최대 관측값은 35.78%, 최소 가용 RAM은 42.20384%, 검사 프로세스의 machine CPU 최대값은 6.21934%였다. metadata warning 중단은 없었다. 이 관측은 PC 프리즈 해결이나 과거 CPU peak 원인을 입증하지 않는다.

근거는 `evidence/p09-361-case160-isolated-prior159-code9-r762.v1.json`과 `evidence/p09-361-case160-isolated-prior159-code9-r763.v1.json`이다.
